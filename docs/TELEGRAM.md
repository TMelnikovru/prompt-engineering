# Telegram: выбранные чаты и ИИ-контекст

Один серверный аккаунт студента, явный список разрешённых чатов, PostgreSQL и
OpenAI Responses API. Это режим одного оператора; разделения нескольких студентов
нет. Приложение читает сообщения и PDF, не вступает в чаты, не пишет сообщения и
не отмечает их прочитанными.

## Подключение

1. Получите собственные `api_id` и `api_hash` через
   [Telegram API development tools](https://core.telegram.org/api/obtaining_api_id).
2. Создайте `.env` из `.env.example`, если его ещё нет. Локально задайте
   `HSE_DATABASE_URL`, `HSE_TELEGRAM_API_ID`, `HSE_TELEGRAM_API_HASH`,
   `OPENAI_API_KEY`, `HSE_SUMMARY_MODEL` и случайный `HSE_INGESTION_TOKEN`.
   Модель выберите из доступных вашему OpenAI-проекту. Не пересылайте секреты в чат.
3. Выберите чаты через `HSE_TELEGRAM_CHATS`: JSON-массив ID или `@username`.
   Для выбранного пользователем канала: `["@dsba_hse"]`.
   Принимается и `https://t.me/DSBA_HSE`; ссылки-приглашения не используются.
4. Выполните на том сервере, где будет работать чтение:

```sh
uv sync --frozen
uv run alembic upgrade head
uv run python -m app.telegram_cli login
uv run python -m app.telegram_cli dialogs
```

Номер телефона, код и пароль двухэтапного входа вводятся скрыто в интерактивном
терминале. `dialogs` показывает названия и ID групп/каналов и заполняет кеш
идентификаторов Telethon. Для приватного чата используйте ID из этого списка.
Сессия сохраняется в `.sessions/telegram.session`; каталог создаётся с правами 700,
файл — 600. Путь можно переопределить через `HSE_TELEGRAM_SESSION_PATH` (с окончанием
`.session`). Файлы сессии исключены из Git и Docker build context. Не копируйте их
в отчёты: сессия предоставляет доступ к аккаунту. Login, worker и HTTP-синхронизация
используют файловую блокировку общей сессии.

## Запуск

```sh
# Одно обновление выбранных чатов и сводки
uv run python -m app.ingest sync-telegram --summarize

# Постоянный процесс на сервере, независимо от вкладки браузера
uv run python -m app.ingest telegram-worker --summarize

# Веб-интерфейс в другом процессе
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте `/telegram`, введите ключ доступа оператора (`HSE_INGESTION_TOKEN`). Он
остаётся только в памяти вкладки. «Прочитать чаты и обновить сводку» запускает
ту же синхронизацию и анализ, которые использует worker. Не передавайте ключ в URL.
Для удалённого доступа используйте HTTPS. В сводке видны темы, договорённости,
задания, открытые вопросы, противоречия и ссылки на сообщения.

Действующие маршруты с заголовком `X-Ingestion-Token`:

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/v1/integrations/telegram/sync` | Только чтение Telegram и сохранение |
| POST | `/api/v1/knowledge/telegram/refresh` | ИИ-сводка сохранённых сообщений |
| GET | `/api/v1/knowledge/telegram` | Сохранённая сводка и признак `stale` |
| GET | `/api/v1/documents?source_id=telegram` | Сообщения в общей библиотеке |
| GET | `/api/v1/documents/{id}` | Текст, метаданные и число версий сообщения |
| GET | `/api/v1/sources` | Состояние источника и последнего обновления |

Без токена закрыты все маршруты библиотеки, включая вики и прежнюю общую сводку.
Публичный dashboard содержит только состояния подключений, без переписки.
Коды ошибок не содержат ответов Telegram, текстов сообщений или секретов.

## Docker Compose

Сессия хранится в отдельном постоянном volume `telegram_sessions`, общем для
веб-приложения и worker. Добавьте `COMPOSE_PROFILES=telegram` в серверный `.env`,
чтобы автоматическое развёртывание обновляло также Telegram-worker. Используйте
тот же `--project-name` и `--env-file`, что и при обычном развёртывании:

```sh
docker compose build app
docker compose up -d postgres
docker compose run --rm --no-deps app python -m alembic upgrade head
docker compose --profile telegram run --rm --no-deps telegram-worker python -m app.telegram_cli login
docker compose --profile telegram run --rm --no-deps telegram-worker python -m app.telegram_cli dialogs
docker compose --profile telegram up -d app telegram-worker
docker compose --profile telegram logs --tail 50 telegram-worker
```

В Docker используется `/app/.sessions/telegram.session`; локальное переопределение
пути для другого окружения не переносится в контейнер. Удаление volume потребует
повторного входа. Процесс перезапускается через `restart: unless-stopped`.

## Границы чтения и доверия

- По умолчанию первая загрузка охватывает последние 7 дней. `HSE_TELEGRAM_HISTORY_DAYS`
  меняет окно; изменение запускает повторное чтение окна с устойчивыми ID.
- `HSE_TELEGRAM_BATCH_SIZE=200`: страница читается от старых сообщений к новым.
  Курсор записывается в PostgreSQL после сохранения страницы; большой поток не
  пропускается при перезапуске. Незавершённая загрузка имеет `has_more=true`, статус
  `partial`. Пустой, но успешно прочитанный чат считается доступным.
- ID записи — пара ID чата и сообщения. Правка создаёт версию, повторное чтение
  не создаёт документ-дубликат. Сохраняются исходная ссылка, UTC-время публикации,
  правки и получения, ID ответа и сведения о PDF. Последнее успешное обновление
  не перезаписывается при ошибке.
- На каждом опросе повторно читаются последние `HSE_TELEGRAM_EDIT_SCAN_LIMIT=100`
  сообщений каждого выбранного чата. Более старые правки и удаления сообщений
  автоматически не отслеживаются. Это явное ограничение текущего коннектора.
- Сводка строится непосредственно по контексту последних сообщений, включая
  ответы и правки, а не по изолированным пересказам каждого сообщения. По умолчанию
  берутся последние `HSE_TELEGRAM_SUMMARY_MESSAGES=200` сообщений всех выбранных
  чатов за заданное окно. Лимит текста — `HSE_AI_CHUNK_CHARS * HSE_AI_MAX_CHUNKS`.
  Усечение помечается `coverage=partial`. Убранные из настроек чаты исключаются из
  новых сводок; ранее сохранённые сообщения остаются в защищённой библиотеке.
- Цитаты заданий проверяются по исходному тексту, сроки сохраняются дословно без
  выдуманного года или времени. Для утверждений требуются существующие ID сообщений.
  При переносах и противоречиях модель должна объяснить версии с источниками.
  Это кандидаты и контекст, не готовый план дня и не подтверждённые обязанности.
- PDF скачиваются через MTProto. По умолчанию предел — 8 MB, 30 страниц и 40 000
  символов на вложение. Пределы задаются `HSE_TELEGRAM_PDF_MAX_*`. Для сканов нужен
  OCR, которого пока нет. Ошибка, шифрование и усечение PDF сохраняются явно;
  остальные чаты продолжают обновляться.
- Обычный интервал — `HSE_TELEGRAM_INTERVAL_SECONDS=120`; при ошибке повтор через
  30 секунд. FloodWait увеличивает задержку согласно ответу Telegram. Если OpenAI
  недоступен, сообщения остаются в БД, а сводка повторяется следующим циклом.
  Неизменный вход и модель используют кеш без повторного платного запроса.

## Проверки

```sh
uv run ruff check .
uv run ruff format --check .
uv run pytest
uv run python -m scripts.export_openapi --check
```

Для интеграционных проверок задайте `HSE_TEST_DATABASE_URL` отдельной БД с суффиксом
`_test`. Проверяется PostgreSQL, версии, курсор после перезапуска, отказ одного
чата, восстановление после HTTP 429 OpenAI, отклонение выдуманной цитаты и защита
чтения. Telegram в тестах заменён транспортным двойником MTProto; это не проверка
реальной авторизации. OpenAI проверяется реальными HTTP-запросами к локальному
обработчику из `postman/mocks/openai`. Синтетические сообщения тестов не являются
живыми данными и не включают подключение.

Первичная проверка 2026-10-25: `https://t.me/s/DSBA_HSE` вернул HTTP 200 и 17
публичных сообщений. Это проверка веб-предпросмотра; MTProto-вход, чтение с сервера
команды и платный запрос модели без настроенных учётных данных не проверены.
Orbit не предоставил подходящий контракт истории пользовательских чатов;
использованы первичные источники:
[Telethon client API](https://docs.telethon.dev/en/stable/modules/client.html),
[Telegram sessions](https://docs.telethon.dev/en/stable/concepts/sessions.html).

## Передача следующему ИИ-агенту

Ветка `telegram` основана на `backend/postgresql` (исходно commit `641caab`). В неё
влит текущий `backend/postgresql` (`d727c3e`: интерфейс ВШЭ из main и общий контракт
источников). После слияния страница `/telegram` использует стили нового интерфейса,
ссылка «Сводка Telegram» добавлена в меню «Учёба», а `/api/v1/sources` по-прежнему
требует `X-Ingestion-Token`; главная страница читает только публичный dashboard.
Проверки после слияния: Ruff, 34 теста с PostgreSQL 16 и OpenAPI; страницы `/` и
`/telegram` просмотрены в браузере без данных Telegram.
Задача пользователя — читать выбранную учебную переписку и давать через ИИ общее
понимание обсуждений. Подтверждённый канал: `https://t.me/DSBA_HSE`.
В новом окружении задайте `HSE_TELEGRAM_CHATS=["@dsba_hse"]` в локальном `.env`:
этот файл, API-ключи и сессия в Git не передаются.

Код коннектора, PostgreSQL-сохранение, фоновый процесс, API и страница `/telegram`
реализованы. При передаче прошли 32 теста с отдельным PostgreSQL, Ruff и проверка
OpenAPI; интерфейс просмотрен в браузере на синтетических сообщениях. Отдельно
проверен вызов ИИ-сводки через локальную Postman simulation и повторное использование
кеша. Живая авторизация Telegram и запрос к настоящей модели не проверены.

Следующие действия:

1. Прочитайте `AGENTS.md` и эту инструкцию; продолжайте из `origin/telegram`.
2. Настройте параметры Telegram, PostgreSQL, модель, ключ OpenAI и токен оператора
   на сервере. Вход выполнит владелец аккаунта через интерактивный CLI.
3. Запустите `sync-telegram --summarize` для `@dsba_hse`, проверьте реальные сообщения,
   исходные ссылки и сводку на `/telegram`. Не подменяйте эту проверку веб-превью.
4. Запустите постоянный Telegram-worker. Проверьте появление нового сообщения,
   правку срока, восстановление после перезапуска и отсутствие дублей.
5. Зафиксируйте фактические результаты и оставшиеся ограничения. Готовый коннектор
   без успешного чтения с сервера не означает подключённый источник или готовый MVP.
